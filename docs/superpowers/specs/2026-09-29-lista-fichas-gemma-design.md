# Lista y fichas de productos con Gemma local

Estado: diseño conversacional y documento aprobados por el usuario el 29 de septiembre de 2026.

## Objetivo y alcance

El usuario del bot de Telegram quiere preguntar en español por su lista guardada y por productos observados previamente en tiendas, además de añadir un producto a la lista con frases como «necesito arroz». Gemma 4 E2B debe entender que actúa como asistente de compras, no como chat general; SQLite es la fuente de verdad. Las respuestas deben ser útiles sin atribuir actualidad a observaciones antiguas ni inventar datos. El éxito se comprueba con el bot vinculado, además de pruebas offline, antes de habilitar esta funcionalidad para uso cotidiano.

Esta fase no incluye compras, preparación de carritos, histórico de pedidos, navegación nueva por tiendas ni scraping automático. No cambia la configuración privada, los permisos de Telegram, las restricciones de productos ni las capacidades live de las tiendas. El modo `dry_run` y los comandos existentes siguen disponibles aunque Ollama falle. No usar API externa como fallback.

## Datos persistentes

- **Lista:** reutilizar `list_lines` y sus reglas actuales. Ninguna «memoria» conversacional de Gemma sustituye esta tabla. Tras un reinicio, la lista y los IDs deben permanecer iguales.
- **Fichas observadas:** crear un catálogo local estructurado y fechado a partir de las observaciones públicas ya existentes en el repositorio. Cada ficha identifica tienda, producto, URL pública de origen, fecha de observación, descripción/formato y solo los atributos efectivamente observados (precio y disponibilidad si constan). Conservar restricciones y estado de verificación; una URL que contenga un GTIN no acredita por sí sola ese GTIN. Los datos ausentes se representan como ausentes, no como cero, disponibilidad positiva o envío gratis. No incorporar datos personales ni HTML sin depurar. La importación inicial es reproducible, idempotente y revisable; no presenta los precios de septiembre como actuales ni alimenta automáticamente decisiones de checkout.
- **Pendientes de investigación:** guardar en SQLite una solicitud de producto normalizada cuando una consulta inequívoca de producto no encuentre ficha. Guardar solo el nombre mínimo del producto y fecha, no el mensaje entero, token, dirección ni historial. Evitar duplicados mediante clave estable. El backlog es para un siguiente scraping manual o planificado por separado: este cambio no lo ejecuta ni convierte la solicitud en alta de lista o permiso de compra. Consultas genéricas y nombres no identificables no generan pendientes.

## Flujo de conversación

1. Telegram conserva la autorización actual, el inbox duradero y la deduplicación. El código lee una instantánea acotada de la lista y recupera fichas relevantes para el mensaje antes de invocar al intérprete local. La recuperación es controlada por el bot: Gemma no recibe herramientas de SQL, archivos, red ni tiendas; no decide cuándo navegar. La selección de fichas es por coincidencia comprobable de nombre/alias, con límite de resultados y datos mínimos. Texto de fichas y mensajes se trata como datos no fiables, nunca instrucciones.
2. Los comandos deterministas (`/lista`, `/anadir`, `/quitar`, `/cantidad`, `/comprar`, etc.) mantienen prioridad y comportamiento. Para mensajes libres, el intérprete propone una intención tipada: consultar lista, consultar producto, añadir un producto, o pedir aclaración. Una pregunta sobre la lista no se transforma en un alta; una consulta de producto no desencadena compra ni cambia la lista.
3. Para «necesito arroz» se propone `add` con la descripción exacta `arroz`, sin inventar marca, variedad ni cantidad. El validador de `Conversation` comprueba que se conserva el texto solicitado y que no hay negación, condición, producto alternativo, varios productos o cantidad ambigua. Si falla, no muta la lista y pide aclaración. Mantener la validación reforzada para fórmula, pienso y pañales; no sustituir referencias restringidas. Los comandos explícitos siguen siendo la vía para cantidades y acciones destructivas. El modelo nunca inicia `buy`, `resume`, `remove` ni `set_quantity`.
4. Las respuestas sobre lista y fichas se construyen con datos recuperados, no con recuerdos del modelo. Se puede usar Gemma para expresar la respuesta, pero los hechos, campos y fechas deben estar anclados en datos estructurados y validados; preferir una respuesta determinista cuando no se pueda demostrar ese anclaje. La lista describe el estado actual; cada ficha se presenta como observación histórica con fecha y fuente. No afirmar cobertura de todas las tiendas, stock o precio actual, ni precio final con envío cuando se desconoce.
5. Si falta una ficha para un producto identificable, la respuesta indica la ausencia y confirma que quedó pendiente de investigación. Guardar el pendiente y la respuesta mediante el flujo duradero existente para que reintentos del mismo mensaje no creen duplicados. Si no se puede reconocer inequívocamente un producto, pedir aclaración y no generar backlog. Un fallo o timeout de Ollama no crea pendientes ni mutaciones; informar del fallo y ofrecer comandos.

## Seguridad y límites operativos

- Ollama continúa restringido a `127.0.0.1:11434`, sin proxy/redirecciones ni envío de secretos. Enviar solo el texto del mensaje, lista mínima y fichas pertinentes: nunca configuración privada, direcciones, credenciales, historial entero ni datos de pago.
- Un límite total de tiempo protege el worker durante cargas frías; no retrasar indefinidamente la recepción duradera. Sin respuesta válida, fallar de forma segura. Ninguna salida del modelo es autoridad para ejecutar SQL, abrir navegador o autorizar checkout.
- Las fichas son observaciones no verificaciones de compra: conservar las barreras existentes de catálogo, cotización y `live_verified=False`. Una solicitud de backlog tampoco verifica un producto.
- No registrar cuerpos de mensajes ni respuestas privadas de Ollama. Respuestas y backlog no exponen datos de otros usuarios; el bot sigue siendo de un único usuario autorizado.

## Verificación y entrega

Pruebas TDD de recuperación de fichas y lista, importación idempotente, consultas, falta de ficha/backlog sin duplicados, deduplicación/reinicio, fallos del modelo y seguridad de negaciones, variantes y productos restringidos. Pruebas de frases en español con el modelo real en este equipo: «necesito arroz» debe dar de alta una sola línea sin cantidad; «¿qué hay en mi lista?» debe leerla; una pregunta por un producto observado debe mostrar fecha y atributos presentes; una pregunta por producto ausente debe guardarlo una vez en backlog; «no compres» no debe crear orden ni alterar la lista. Medir latencia de primera carga y caliente, y VRAM; no dar por válida la función solo porque pasan fakes. Si E2B no alcanza fiabilidad suficiente, no habilitarlo y conservar comandos hasta corregirlo o decidir otra estrategia con el usuario. No hacer compras reales ni pulsar `/comprar` en pruebas de aceptación.

La instalación autorizada de Ollama y `gemma4:e2b` ya existe en este ordenador; la prueba anterior mostró que el prompt actual no interpreta bien «necesito arroz». Esta especificación no autoriza cambios en el bot privado ni una publicación de rama: la activación de Telegram se realizará solo cuando las pruebas de calidad y el entorno privado lo permitan.
